# Initial Feasibility Study

## A. Technical Feasibility

The system can realistically be built with the team's existing skills. Java Servlets, JDBC, MySQL, JSP, HTML/CSS/JS, and Bootstrap are all technologies the team has prior experience with. The OpenAI API and Apache PDFBox introduce some learning curve, but both are well-documented and widely used, making them achievable within the project timeline.

## B. Economic Feasibility

Expected costs are low. Development tools (Java, MySQL, IDEs, GitHub) are free for academic use. The main cost is OpenAI API usage (billed per token), which can be kept minimal by using a lightweight model and monitoring usage during development. No hosting costs are required for a course-scale deliverable.

## C. Operational Feasibility

The system solves a real problem — manual flashcard creation is tedious, and students already rely on similar tools (e.g., Quizlet, Anki) informally. Given this existing demand, user acceptance is likely to be high if the AI-generated flashcards are accurate and the interface stays simple.

## D. Schedule Feasibility

With the Incremental model, core features (auth, CRUD) can be completed early, followed by AI flashcard generation, then analytics/dashboards in later increments. This ensures a functional core product exists even if later features are delayed.

## E. Overall Feasibility

StudyBuddy is considered feasible overall. The team has the needed technical skills, costs are minimal, the system addresses a genuine student need, and the scope is achievable within the semester when developed incrementally. The main risks to watch are the team's limited experience with the OpenAI API/PDF parsing and reliance on a third-party API outside the team's control — both manageable through early prototyping and the mitigation strategies in the Risk Register.
